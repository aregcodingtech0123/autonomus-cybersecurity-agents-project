# Architecture decisions

One record per decision that is expensive to reverse or easy to forget the reason for. Newest last.

## ADR-001: Semgrep registry rules are used for local, user-initiated runs only

- **Status:** accepted (Phase 2B, 2026-11-03)
- **Decision:** Semgrep registry rules are under the Semgrep Rules License v1.0; the project uses them for
  local, user-initiated runs only; rules are never committed or redistributed; revisit with own custom rules
  before any hosted deployment.
- **Consequences (what this means in the repository):**
  - `secaudit rules update` fetches the rulesets into `.secaudit/rules/` (git-ignored). Nothing under that
    directory is ever committed, packaged into an image, or attached to a release.
  - CI fetches the rules fresh inside the Docker job and deletes them at the end. The workflow has no
    `upload-artifact` and no cache step, which `tests/test_ci_workflow.py` asserts.
  - The committed baseline records only the rule snapshot's names and SHA-256 hashes
    (`benchmarks/baseline/manifest.json`), not the rules. The strict parity test therefore skips, with a stated
    reason, when a machine's snapshot differs from the recorded one.
  - Reports and the database carry rule ids, short names and the finding's own message. They do not embed
    rule bodies or whole rule files.
- **Open:** a hosted or distributed product cannot rely on the registry rules. Before any such deployment,
  replace them with project-owned custom rules (the Phase 2C/3 roadmap already needs custom rules for P08, P10
  and P11, which no registry rule detects) or obtain a license. Until then this ADR is the boundary.
- **Related:** `docs/PHASE1_NOTES.md` (license summary), `docs/ROADMAP.md`.

## ADR-003: No provider-shaped value anywhere; the benchmark's planted secrets are generic-shaped

- **Status:** accepted (2026-11-03), before the repository's first push
- **Context:** GitHub push protection scans every commit of a push and blocks provider-shaped tokens even
  when they are fake. The benchmark planted a Stripe-shaped API key (P02), an AWS-shaped key pair (P03) and
  AWS's documented example pair (N07). Their copies also sat in the committed raw scanner outputs and in the
  frozen Phase 1 fixture. Allowlisting them would mean asking for an exception on every push.
- **Decision:** every planted fake is replaced with a generic-shaped fake of exactly the same length: a
  `bench_` prefix and a random base62 body, which matches no provider format. Line structure, SARIF
  columns and byte counts of the mapped files stay the same. The two N07 values keep the allowlisted word
  at the end (`EXAMPLE`, `EXAMPLEKEY`), like the AWS originals, so Gitleaks' stopword list still skips
  them. The old -> new mapping holds the old values and is kept outside the repository; it is never
  committed. The local history was rewritten with the same mapping before the first push.
- **The one exception to the frozen-baseline principle:**
  - `benchmarks/baseline/raw/` and `manifest.json` were **regenerated by a real sandboxed container scan**
    of the modified target (`benchmarks/regenerate_baseline.py`, audit `20261103T161647Z-68eba1f9`), never edited by hand;
    `metrics_tool_only.{json,md}` were rewritten by `secaudit eval`.
  - The frozen records the current pipeline cannot reproduce (`tests/fixtures/phase1_baseline/**` and the
    native discovery runs in `benchmarks/baseline/raw_native/**`) were **re-scrubbed by the same exact-length
    text mapping** with `benchmarks/rescrub_frozen.py`, which recomputes the hashes recorded in the fixture
    manifest (raw artifact hashes, and the input tree hash with the intake's own formula, first proven by
    reproducing the recorded value). Their rule ids still describe the original shapes (for example
    `stripe-access-token`), because that is what the tools reported at the time.
- **Proof of structural equivalence:** applying the mapping to the old raw files and comparing with the
  regenerated ones gives: `semgrep.sarif` byte-identical; `bandit.sarif` differs only in `endTimeUtc`;
  `semgrep.json` only in `time.*`; `pip-audit.json` only in the order of `aliases` (equal as sets). In
  `gitleaks.sarif` everything outside `results` is identical, line 8 is identical, line 3 changed rule
  (`stripe-access-token` -> `generic-api-key`, so `message.text` and `startColumn` 21 -> 2), and line 7 is
  no longer reported (below).
- **Consequences (explained differences, not hidden):**
  - Gitleaks reports **2** results instead of 3. Its generic rule allowlists identifiers matching `key_id`,
    so `aws_access_key_id = bench_...` (P03, line 7) is not reported once the AWS-specific rule no longer
    applies. Verified by a container run: renaming that identifier restores the result. The owner chose to
    keep the identifier and accept 2 results.
  - P03 is re-described as "secret token in an .ini configuration file, detected by a generic rule" and is
    still detected (line 8). P02 is still detected by Bandit (line 4) and Gitleaks (line 3); N07 is still
    not reported. Bandit 16, Semgrep 11 and pip-audit 16 results are unchanged.
  - Normalized findings 25 -> 24 and raw results 46 -> 45 (the line-7 hit); tests that pin those counts were
    updated. Detection metrics are unchanged: **9/12 positives, 4/7 negatives**, and 9/11 for the Phase 1
    fixture with `--exclude P11`.
  - Historical commits carry mapped values next to hashes that were computed from the old values, so their
    pinned hashes are stale. Only HEAD is required to be consistent and green.
- **Enforced by:** `tests/test_no_secret_literals.py` scans every tracked file with **no allowlist**.
- **Related:** `docs/SECURITY_POLICY.md` section 7, `benchmarks/baseline/DISCOVERY.md` Addendum 5.
